# Session 10 — Meetups

Tracks progress against the Session 10 scope in
[`trib4l-build-from-zero.md`](./trib4l-build-from-zero.md#phase-1--community-core-sessions-3-10):
"Events, RSVP, attendance recording, recurrence in the organizer's
timezone. Attendance is a first-class record an organizer can mark
manually, so the metric survives regardless of where the call happens.
Store `meeting_provider` plus URL rather than hardcoding an external
link — later, `provider = 'livekit'` is a swap, not a migration." No
explicit "done means" line for this session — same bar as prior sessions
applied here.

## Done and verified

- [x] **`meetup_series` and `meetups` are deliberately two tables, not
  one.** A series is the recurrence template (cadence, timezone, meeting
  info); a row in `meetups` is one concrete, bookable occurrence.
  RSVPs and attendance attach to a *specific* occurrence, which needs a
  stable id — a computed-on-the-fly occurrence from a recurrence rule
  wouldn't have one — so occurrences are real rows, generated explicitly
  via an RPC, not a view over the series.
- [x] **Recurrence is correct across a DST transition — verified, not just
  reasoned about.** A series stores `next_occurrence_date` (a local
  calendar date) plus `local_time` and an IANA `timezone`; each occurrence
  is generated by reinterpreting that same local wall-clock time in the
  zone fresh, on its own date (`(date + local_time) at time zone tz` in
  Postgres, which owns the IANA timezone database). This is what makes
  "recurrence in the organizer's timezone" actually correct: a fixed
  UTC-interval approach would drift the wall-clock time by an hour
  whenever a DST transition falls between two occurrences. Checked
  directly, twice: once via a raw SQL query against `local_datetime_to_utc`
  spanning the 2026-03-08 US spring-forward (confirmed 6pm Eastern stays
  6pm Eastern — 23:00 UTC before the transition, 22:00 UTC after), and
  again through the real `generate_meetup_occurrences` RPC end-to-end in
  an isolation test.
- [x] **`meeting_provider` is plain `text`, deliberately not an enum or a
  `CHECK`-constrained list** — the plan calls this out by name
  ("`provider = 'livekit'` is a swap, not a migration"), and an enum or a
  check list would need exactly the migration that decision exists to
  avoid.
- [x] **Attendance is its own table, independent of RSVP and of
  `meeting_provider`** — `meetup_attendance`, marked manually by staff,
  with no dependency on any video/call platform. This is what the plan
  means by "the metric survives regardless of where the call happens":
  attendance isn't derived from any provider's analytics, and none of
  that integration exists yet (Session 11+).
- [x] **RSVP visibility follows Session 8's minimal-by-default
  precedent**: your own row, or staff (who need headcounts) — not "see who
  else is going." The same reasoning `member_stages_select` used: what
  someone else RSVPed isn't something a peer needs to browse, only staff
  running the meetup.
- [x] **Meetups reuse Session 6's `can_see_org_cohort_content` directly**
  for org/cohort-scoped visibility — no stage gating (Session 8's
  `is_at_or_past_stage`) was added, since nothing about scheduling a call
  needs it and it wasn't asked for.
- [x] **RLS + grants shipped together**, same discipline as every prior
  session. 6 isolation tests (`tests/isolation/meetups.test.ts`): staff
  can create a one-off meetup, a plain member cannot; the DST-crossing
  recurrence test above; a member can RSVP only as themselves, and
  changing their mind updates the same row rather than creating a second
  one; an RSVP is visible to its owner and staff but not an unrelated
  member; only staff can mark attendance (not even the attendee
  themselves), visible to the marked person and staff but not an outsider;
  a cohort-scoped meetup is invisible to a member outside that cohort. 51
  total isolation tests now pass.
- [x] **The escalation test genuinely fails loudly when loosened** —
  checked directly: temporarily replaced `meetups_select`'s policy with
  `using (true)`, watched the cohort-scoping test fail with the real
  visible row printed, restored via `supabase db reset`, confirmed all 51
  pass again.
- [x] **A recurring methodology issue caught again, not repeated
  blindly**: manually checking access control against seeded Alice
  initially showed her passing a staff-only check she shouldn't have —
  because the isolation suite's last full run (immediately before
  starting the dev server) had durably promoted her role in the same
  shared local database, same pattern flagged in Sessions 8 and 9's
  checklists. Confirmed directly via a query against `memberships` before
  concluding it wasn't a real bug, then reset to clean seed data and
  redid the manual pass with a genuinely plain member.
- [x] **UI**, same plain styling as prior sessions, manually driven
  through the real dev server (curl simulating real form submissions,
  extracting the real `$ACTION_ID` fields), on a freshly reset database:
  - A staff settings page (`/o/[slug]/settings/meetups`): create a
    one-off meetup (with explicit start/end local date+time+timezone,
    converted server-side via `local_datetime_to_utc`), create a
    recurring series, a "Generate next 4" button per series, and a list
    of upcoming meetups with RSVP counts and manual attendance
    marking/unmarking.
  - A member-facing page (`/o/[slug]/meetups`, linked from the main nav
    for everyone): upcoming meetups with the meeting link and an RSVP
    selector.
  - Confirmed the full flow end-to-end with real accounts: created a
    one-off meetup and a weekly series as Bob (organizer), generated four
    real occurrences and confirmed their `starts_at` values in the
    database directly, confirmed a plain member is redirected away from

    trace of the form in the response body, not just an assumed
    behavior), RSVPed as a plain member through the real member-facing
    form, and confirmed the RSVP count updated on the staff page.

## Not done in Session 10 — explicitly out of scope here

- **Displaying meetup times in the viewer's or the organizer's chosen
  timezone in the UI.** The stored `starts_at`/`ends_at` are correct
  (verified directly against Postgres), but the pages render them with
  a plain `toLocaleString()`, which uses the rendering server's own
  system timezone, not the viewer's or the organizer's. This is a display
  wrinkle, not a data-correctness bug — the underlying timestamptz values
  are right regardless of how any given page happens to format them —
  but it's worth fixing before this UI is relied on by real users.
- **Automatic/background occurrence generation** (e.g., a cron job that
  keeps a series topped up without a staff member clicking "generate").
  Every occurrence in this session is created by an explicit staff
  action, matching Session 8's "every transition is a deliberate action"
  precedent for the same kind of scope question.
- **RSVP or attendance for meetups a person can no longer see** (e.g.,
  after being moved out of a cohort). Not tested or specifically
  designed for; the general org/cohort-scoping RLS applies uniformly, but
  no dedicated behavior was built for this edge case.
